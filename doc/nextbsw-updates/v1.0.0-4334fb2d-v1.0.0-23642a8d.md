# neXtBSW-Update 1.0.0 (4334fb2d) -> 1.0.0 (23642a8d)

Entwicklungs-Pin auf Entwicklungs-Pin, beide ohne Release-Tag (`nextbsw.yaml`, customer-project.md 4.4).
Umgezogen am 2026-11-04 im Zweig `pin-io125` auf Auftrag des Koordinators (IO-125 auf neXtBSW `dev` gemergt). Von Hand nach Abschnitt 5.5.

## Was neu ist, soweit es BattSimFW betrifft

- **IO-125** Pull-up je I2C-Leitung im Board (`i2c[].sda/scl.pull`, nur `up`, PULLUP im PCR der Leitung) und `clock.output_dividers` im Projekt
  (Teiler eines asynchronen SCG-Ausgangs, z. B. `SPLLDIV2: 64`, damit FlexIO-I2C unter 31,25 kHz kommt; BattSim: SPLLDIV2 / 64 = 2,5 MHz -> 9541 Hz).
  Ein zu langsamer SCL meldet nxconfig jetzt mit Hoechsttakt und Einstellungen je Quelle.
- Sonst Motor-/Safety-/Doku-Themen der Eval-Board-Seite (SYS-245/265/269/270/271/272, TOOL-309, DOC-113): wirken im BattSim-Abbild nicht.
- Das verschachtelte Untermodul `external/openbsw` bleibt auf 6e06d961 (2026.10) (`git submodule update --init external/openbsw` im nextbsw).

## Was in BattSimFW geaendert wurde (Variante 1: 31,25 kHz, Board io125-blockieren a)

| Datei | Aenderung |
|---|---|
| `nextbsw.yaml`, `nextbsw` | Pin auf 23642a8d |
| `boards/battsim_master_v1/board.yaml` | `i2c[DISP_I2C].scl.pull: up` (PTE16, wie die Werksfirmware); SDA (PTE15) bleibt ohne Pull-up |
| `projects/battsim_master/project.yaml` | `i2c.DISP_I2C: {baudrate_hz: 31250, timeout_ms: 5}` (vorher 100000 / 2); **kein** `clock.output_dividers` |

Warum 5 ms: nxconfig verlangt ein Zeitlimit mindestens so lang wie die laengste Uebertragung des Treibers (13 Datenbytes = 4,32 ms bei 31,25 kHz); 4 ms wurde abgelehnt.
Folge: haengt der Takt, kann der 10-ms-Task schlimmstenfalls um 2 x 5 ms = 10 ms laenger werden (vorher 4 ms). Ein Byte dauert real etwa 1 ms. Im Normalfall ohne Wirkung.
